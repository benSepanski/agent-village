# Key property: concurrent access to the same state

**The property:** the invariants that matter financially or for auditability — the spend cap and run immutability — hold under arbitrary concurrency, because they are enforced by single atomic DynamoDB conditional writes, not by read-then-write sequences. Everything else is last-writer-wins by design.

## What is protected, and how

| Invariant                                                                                 | Mechanism                                                                                                                                                                                                                     | Code                                                                                                                                                             |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two concurrent runs cannot jointly exceed `spendLimitUsd`                                 | Reservation is one atomic `UpdateItem` with `ConditionExpression: spendUsedUsd + :estimate <= spendLimitUsd`. DynamoDB serializes the check-and-increment; the loser gets `SpendLimitExceededError` and never calls Anthropic | [`reserveSpend()` in `dynamo/agents.ts`](../../packages/data/src/dynamo/agents.ts), pattern explained in [spend-reservation](../data-model/spend-reservation.md) |
| A run record can never be written twice or overwritten                                    | Each run gets a fresh ULID and is persisted with `ConditionExpression: attribute_not_exists(pk)` — a duplicate write fails instead of clobbering                                                                              | [`append()` in `dynamo/runs.ts`](../../packages/data/src/dynamo/runs.ts)                                                                                         |
| A failed run cannot permanently inflate the accumulator                                   | Failures before finalization refund the reservation with a negative delta; the refund itself failing is logged as `agent.run.spend_refund_failed`                                                                             | [`refundReservation()` in `runner.ts`](../../packages/services/src/runner.ts)                                                                                    |
| Two concurrent schedule writes for the same agent cannot error out or duplicate schedules | Schedule names are deterministic (`agent-<agentId>`); `CreateSchedule` falls back to `UpdateSchedule` on `ConflictException` — an idempotent upsert, last writer wins                                                         | [`upsertSchedule()` in `services/scheduling.ts`](../../packages/services/src/scheduling.ts)                                                                      |
| Updates cannot resurrect a deleted agent                                                  | `updateAgent` carries `ConditionExpression: attribute_exists(pk)`                                                                                                                                                             | [`updateAgent()` in `dynamo/agents.ts`](../../packages/data/src/dynamo/agents.ts)                                                                                |
| Two CI deploys cannot run CloudFormation on the same env at once                          | GitHub Actions `concurrency` group per ref                                                                                                                                                                                    | [`deploy.yml`](../../.github/workflows/deploy.yml)                                                                                                               |

## What is deliberately last-writer-wins

- **Agent config updates.** There is no version attribute or optimistic locking on the agent item; concurrent `PATCH /agents/:id` calls overwrite each other field-by-field. Acceptable for a single-operator UI.
- **Spend finalization.** The post-call correction is an unconditional `ADD` ([`finalizeSpend()`](../../packages/data/src/dynamo/agents.ts)); it commutes, so ordering doesn't matter.

## Known limits

- **No per-agent run mutual exclusion on the inline path.** A scheduled fire and a "Run now" click can execute the same agent concurrently. Each run independently reserves spend, so the cap holds, but both calls happen. The one-run-per-agent guard is specified for the sandbox launcher (Phase 2 step 05, [phase-2-sandbox-runs](../phases/phase-2-sandbox-runs.md)) and the launcher does not exist yet.
- **No idempotency tokens on the API.** A retried `POST /agents/:id/run-now` produces two runs; a retried `POST /agents` produces two agents.
- EventBridge Scheduler may retry a failed runner invocation; because the run ULID is minted inside the invocation, a retry is a _new_ run, not a duplicate write.
