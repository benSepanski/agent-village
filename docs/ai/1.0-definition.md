# agent-village 1.0 — binding scope definition

This is the **binding** definition of what "1.0" means for agent-village. The
owner (Ben) set the minimum bar; this doc formalizes each bar item into
**testable acceptance criteria**. Nothing ships as 1.0 until every criterion
below is met and the M6/M7 dogfood verdicts are recorded in
[`docs/ai/`](README.md). Scope **additions** require the owner; the
[out-of-scope list](#explicitly-out-of-10-binding) is equally binding against
scope creep.

Each criterion carries: a stable **ID** (`AC-<item>.<n>`), a **statement**, a
**verification method** (unit / integration / E2E / manual-dogfood), and the
**milestone** that delivers it. Report status by ID.

## 1. Auditability

**Bar:** structured event logs + per-run `traceId` + S3 workspace versioning
must let an operator reconstruct any run's full story — who, what, when, cost,
egress.

| ID     | Criterion                                                                                                                                                   | Verified by    | Milestone |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | --------- |
| AC-1.1 | Every run persists a `traceId`; every structured log line for that run carries it; a single Logs Insights filter returns the run's full timeline.           | Integration    | M2        |
| AC-1.2 | From a `traceId` alone an operator can recover: owning user, agent, trigger source, start/stop, outcome, token+USD cost, and egress destinations attempted. | Manual-dogfood | M6        |
| AC-1.3 | Each workspace mutation is recoverable via S3 object versions across runs (versioning on; noncurrent-expiry honored).                                       | Integration    | M2        |
| AC-1.4 | `docs/playbooks/audit-a-run.md` exists and was produced by **actually performing** the trace on a real run; every step in it was executed, not assumed.     | Manual-dogfood | M6        |

## 2. Spend limits

**Bar (AI side):** keep the per-task cap and per-agent lifetime cap (both exist,
atomic reserve→reconcile); **add** per-user aggregate + time-windowed (monthly,
auto-resetting) budgets enforced _in the same atomic transaction_, plus a
drift-reconciliation job with an alarm; all limits transparently visible
(limit / used / remaining) in web UI and CLI. **Bar (AWS side):** document
honestly that Budgets alert-not-block, and document how to add budget actions.

| ID     | Criterion                                                                                                                                                                        | Verified by         | Milestone |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | --------- |
| AC-2.1 | Per-task cap and per-agent lifetime cap remain enforced with no regression (atomic reserve→reconcile; over-cap reservation → `spend_limit_exceeded`, no Anthropic call).         | Unit + Integration  | M3        |
| AC-2.2 | A **per-user aggregate** budget caps the sum of spend across all of a user's agents; a call that would breach it is rejected before Anthropic is hit.                            | Unit + Integration  | M3        |
| AC-2.3 | The per-user budget is **time-windowed (monthly) and auto-resets** at the window boundary without manual intervention or a destructive counter reset.                            | Unit + Integration  | M3        |
| AC-2.4 | Per-user aggregate + windowed enforcement happens **in the same atomic DynamoDB transaction** as the agent-level reserve — no read-modify-write race admits an over-budget call. | Unit + Integration  | M3        |
| AC-2.5 | A drift-reconciliation job recomputes authoritative spend, corrects accumulator drift, and **raises an alarm** when drift exceeds a threshold.                                   | Integration         | M3        |
| AC-2.6 | Web UI shows limit / used / remaining for each agent **and** for the per-user window.                                                                                            | E2E                 | M4        |
| AC-2.7 | CLI (`village agents show` / a budget subcommand) shows the same limit / used / remaining figures, matching the UI and the ledger.                                               | Integration         | M3        |
| AC-2.8 | Docs state plainly that AWS Budgets **alert, not block**, and give a worked path to add AWS Budget _actions_ for hard enforcement.                                               | Manual (doc review) | M3        |

| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- | --------- |

| AC-3.2 | `docs/playbooks/manage-accounts.md` documents the operator-as-admin model end-to-end (console CRUD + the thin CLI + per-user budgets) and was walked through.                              | Manual-dogfood       | M6        |

| AC-3.6 | **Negative:** no in-app role/RBAC surface exists (no roles endpoint, no role field consumed for authz). Confirms the anti-scope boundary held.                                             | Unit (grep/contract) | M4        |

## 5. Extensibility

**Bar:** a dependent project (e.g. apply-bot) can **either** consume an existing
deployment **or** deploy its own. The config loader
(`packages/infra/config/index.ts`) currently hardcodes `dev`/`prod` — it needs
an `EnvConfig` injection contract for dependent repos, with synth-snapshot tests
proving zero first-party template drift; [app-development.md](../app-development.md)
gains both paths; proven by a real dependent-project fixture exercised locally +
a cold-start doc-following test.

| ID     | Criterion                                                                                                                                                                                    | Verified by         | Milestone |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | --------- |
| AC-5.1 | A dependent repo can inject a validated `EnvConfig` (its own env name, region, account, prefix) **without editing platform source**; the loader no longer hardcodes only `dev`/`prod`.       | Unit + Integration  | M5        |
| AC-5.2 | Synth-snapshot tests prove the first-party (`dev`/`prod`) synthesized templates are **byte-for-byte unchanged** by the injection refactor — zero drift.                                      | Unit (snapshot)     | M5        |
| AC-5.3 | [app-development.md](../app-development.md) documents **both** paths clearly: (a) consume an existing deployment as an app repo, (b) deploy your own platform instance via config injection. | Manual (doc review) | M5        |
| AC-5.4 | A real dependent-project **fixture** synthesizes and (locally) exercises its own instance via the injection contract.                                                                        | Integration         | M5        |
| AC-5.5 | A **cold-start doc-following test**: an agent following only the docs, from a clean state, stands up the dependent path successfully (no tribal knowledge required).                         | Manual-dogfood      | M6        |

## 6. Connectivity

**Bar:** per-agent scoped access stays grants + egress-allowlist +
metering-gateway (**no MCP**). 1.0 ships worked recipes — Anthropic-only agent;
read-only Notion via scoped token + allowlisted host; partial email — each with
an allow-path **and** a deny-path automated test.

| ID     | Criterion                                                                                                                                                     | Verified by          | Milestone |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | --------- |
| AC-6.1 | **Anthropic-only** recipe: allow-path reaches the metering gateway and meters spend; deny-path shows any non-allowlisted host is blocked at egress.           | Integration          | M5        |
| AC-6.2 | **Read-only Notion** recipe: allow-path reads via a scoped token to the allowlisted Notion host; deny-path proves a write attempt / off-allowlist host fails. | Integration          | M5        |
| AC-6.3 | **Partial email** recipe: allow-path sends via the implicit-TLS port to an allowlisted host; deny-path proves STARTTLS / non-allowlisted host is blocked.     | Integration          | M5        |
| AC-6.4 | Each recipe is documented as a self-contained app-repo example (manifest + grants + `egressAllow`) mirroring `examples/gmail-agent`.                          | Manual (doc review)  | M5        |
| AC-6.5 | **Negative (scope):** no MCP transport, no gateway SSE streaming, no STARTTLS path is introduced by these recipes.                                            | Unit (contract/grep) | M5        |

## 7. Dogfooding (owner-mandated testing requirement)

**Bar:** production-readiness includes realistic dogfooding — browser-driven use
of the real UI by AI agents with **distinct personas** (operator,
app-builder-following-the-docs, spend-limit-victim), **local-first**, then a
**user-gated** dev-AWS deployment exercise **preceded by a cost-control
briefing**.

| ID     | Criterion                                                                                                                                            | Verified by    | Milestone |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | --------- |
| AC-7.1 | **Operator persona** drives the real UI (browser) locally: signs in, inspects agents/runs/spend, performs an audit trace, manages an account.        | Manual-dogfood | M6        |
| AC-7.2 | **App-builder persona** builds+runs an app **following only [app-development.md](../app-development.md)** from a separate fixture repo, local-first. | Manual-dogfood | M6        |
| AC-7.3 | **Spend-limit-victim persona** hits per-agent and per-user budgets and observes correct rejection + accurate limit/used/remaining in UI and CLI.     | Manual-dogfood | M6        |
| AC-7.4 | A written **local-dogfood verdict** (go/no-go, with defects filed) is recorded in `docs/ai/` before any AWS deploy is attempted.                     | Manual-dogfood | M6        |
| AC-7.5 | The dev-AWS deploy + live persona dogfood happens **only after explicit user gating** and a **cost-control briefing**; a live verdict is recorded.   | Manual-dogfood | M7        |

## 8. cli-wrapper module (owner scope addition, 2026-07-21)

**Bar:** a module giving sandboxed agents **policy-mediated CLI access** instead
of all-or-nothing: an in-sandbox shim forwards exact argv to a trusted approver
holding the real CLI + credentials; deterministic auto-allow/auto-deny rules
run first, the residue is judged by a **fresh-per-request** approver agent
(allow / deny-with-reason / escalate), and escalation or repeated denials
gracefully kill the run and notify the user. Full design + acceptance criteria
(AC-8.1–8.7): [cli-wrapper-design.md](cli-wrapper-design.md). Expected to
graduate to its own repository post-1.0; the core stays repo-agnostic.

## Explicitly out of 1.0 (binding)

These are **not** 1.0 and must not be introduced under cover of a 1.0 task.
Adding any of them requires the owner to re-open scope.

- Multi-user roles / orgs / RBAC (operator-as-admin only)
- MCP support
- Streaming SSE through the gateway
- STARTTLS egress (implicit-TLS ports only)
- An audit-summarizer agent
- Metering endpoints beyond `POST /v1/messages`
- IdPs beyond Google
- Multi-region / DR
- More than two first-party environments
- A registry-published CLI (tarball install only)

See the [phase 6+ sketch](../phases/phase-2-plus.md) for where several of these
land _later_.
